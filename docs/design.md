# 보안길잡이 AI — KRDS 기반 디자인·UI 개발 규칙

> 문서 버전: **3.0** · 개정일: **2026-11-05**  
> 주 기준: **디지털 정부서비스 UI/UX 가이드라인 2025.08**  
> 비교 자료: **디지털 정부서비스 UI/UX 가이드라인 2024.02 제공본**  
> 대상: 신청자 · 정보보안 담당자 · ICT인프라 담당자 · 기관 관리자  
> 개발 환경: React + Next.js + TypeScript / Spring Boot

이 문서는 보안길잡이 AI의 디자인, UI 구현, 검수에 사용하는 팀 공통 규칙이다. 두 가이드라인의 관련 스타일·컴포넌트·기본 패턴·서비스 패턴을 비교하여 재구성했다. 원문 전체를 대체하지 않으며, 문서에 규칙을 적었다는 사실은 해당 기능의 구현 또는 검증 완료를 뜻하지 않는다.

| 표기 | 의미 |
| --- | --- |
| **가이드 기준** | 출처에서 확인한 규칙을 요약한 것. 원문의 적용 대상·조건·권장 수준을 함께 확인 |

- G25에 없는 프로젝트 업무 규칙은 이 문서에서 명시적으로 정한다.
- 공식 웹 가이드·패키지에 후속 변경이 있으면 영향과 버전을 확인한 후 개정한다. 웹사이트가 바뀌었다고 개발 중인 프로젝트의 규격을 자동 변경하지 않는다.
- 가이드의 ‘필수·권장·우수’와 프로젝트 우선순위는 다른 분류다. 권장 항목을 프로젝트 필수로 채택할 수 있으나 그 결정을 표시한다.
- 원문의 표·본문·코드 예시가 다르게 보이면 단위와 적용 범위를 먼저 확인하고, 해소하지 못한 차이는 이슈로 남긴다.

### 1.2 표준형과 프로젝트 확장

G25는 정부 상징 로고를 사용하는 기관 등의 **표준형 스타일**과 독자적 로고를 사용하는 기관 등의 **확장형 스타일**을 구분한다. 확장형도 사용 규칙을 준수해야 한다. (G25 pp.67–68; G24 p.61)

**프로젝트 규칙**

- 현재 보안길잡이는 자체 서비스명과 와이드 업무 화면을 사용하는 **KRDS 참고 프로젝트 확장 설계**로 관리한다.
- 실제 운영기관이 확정되면 적용 유형, 정부 상징·공식 배너·운영기관 식별자의 사용 범위를 기록한다.
- 개발 편의를 이유로 표준형 대상 서비스를 임의로 확장형으로 분류하지 않는다.
- 정부 상징·‘대한민국 공식 전자정부 누리집’ 문구를 시연 서비스에 임의로 붙이지 않는다.
- 프로젝트 확장값을 사용했다는 이유만으로 검증 결과에 예외(E)를 부여하지 않는다.
- 이 문서는 KRDS 전체 준수 인증이나 접근성·보안 인증 결과가 아니다.

## 3. 제품 원칙과 브랜드

**가이드 기준:** 사용자 중심, 포용성, 일관성과 개별 특성, 간결함, 이해 용이성, 다양한 이용 상황, 신뢰를 함께 고려한다. (G25 pp.49–62; G24 pp.45–58)

**프로젝트 규칙**

1. 공통 토큰·컴포넌트를 재사용한다. 화면마다 별도 색상·버튼 체계를 만들지 않는다.
2. 기관, 담당 역할, 현재 상태, 다음 행동을 계속 확인할 수 있게 한다.
3. 화면 탐색과 업무 상태 변경을 구분한다.
4. 미입력·미확정·미해당·확인 완료를 구분한다.
5. AI 제안과 사람이 확인한 정보를 구분한다.
6. 검토 완료와 실제 처리 완료를 구분한다.
7. 설정 초안·게시본, 문서 편집본·제출본을 구분한다.
8. 오류·통신 실패·시간 초과에도 입력 내용을 복구할 수 있게 설계한다.
9. 키보드, 글자 확대, 작은 화면을 처음부터 함께 설계한다.
10. 실제로 수행하지 않은 저장·알림·AI 처리·업무 완료를 성공으로 표시하지 않는다.

서비스명은 **보안길잡이 AI**, 좁은 헤더에서는 **보안길잡이**를 사용한다. 흰 바탕과 옅은 중립 배경, 파란 주요 행동, 읽기 쉬운 표와 폼을 기본으로 한다. 큰 홍보 배너·과도한 그라데이션·반투명 카드·장식 애니메이션을 업무 화면에 반복하지 않는다. 시연에는 합성 데이터를 사용하고 모의 인증·AI·저장의 범위를 명시한다.

## 4. 색상·토큰·상태·계층

### 4.1 토큰 관리

**가이드 기준:** primitive → semantic → component 계층을 사용한다. 시멘틱 토큰은 역할을, 컴포넌트 토큰은 구체적인 구현 속성을 표현한다. (G25 pp.205–217)

**프로젝트 규칙**

- 공식 토큰을 프로젝트 의미별 별칭 `--sf-*`에 연결한다.
- 공식 원본 CSS를 수정하거나 컴포넌트마다 HEX 값을 복사하지 않는다.
- 새 색상은 재사용 목적·대비 검사·기존 토큰으로 해결하지 못한 이유를 함께 기록한다.
- 기존 프로젝트의 구현 출발점은 `krds-uiux@1.1.0`이다. 이는 패키지 고정 버전이며 **PDF의 발행 버전과 동일한 번호가 아니다**. 실제 저장소의 lockfile을 확인하고 다르면 차이를 기록한다.
- 아래 HEX는 고정 키트의 밝은 모드 매핑 참고값이다. G24 색상표를 섞지 않는다.

| 의미 | 프로젝트 별칭 | 공식 토큰 접미부¹ | 밝은 모드 참고값 |
| --- | --- | --- | --- |
| 주요 버튼 배경 | `--sf-primary` | `button-primary-fill` | `#256EF4` |
| 주요 텍스트 | `--sf-primary-text` | `text-primary` | `#0B50D0` |
| 선택·정보 배경 | `--sf-primary-soft` | `surface-primary-subtler` | `#ECF2FE` |
| 보조 강조 면 | `--sf-secondary-fill` | `element-secondary` | `#063A74` |
| 기본 본문 | `--sf-text` | `text-basic` | `#1E2124` |
| 보조 설명 | `--sf-muted` | `text-subtle` | `#464C53` |
| 기본 바탕 | `--sf-surface` | `background-white` | `#FFFFFF` |
| 보조 바탕 | `--sf-background` | `surface-gray-subtler` | `#F4F5F6` |
| 패널 경계 | `--sf-border` | `border-gray-light` | `#CDD1D5` |
| 오류 텍스트 | `--sf-danger-text` | `text-danger` | `#BD2C0F` |
| 오류 배경 | `--sf-danger-soft` | `surface-danger-subtler` | `#FDEFEC` |
| 보완·주의 텍스트 | `--sf-warning-text` | `text-warning` | `#8A5C00` |
| 보완·주의 배경 | `--sf-warning-soft` | `surface-warning-subtler` | `#FFF3DB` |
| 완료 텍스트 | `--sf-success-text` | `text-success` | `#267337` |
| 완료 배경 | `--sf-success-soft` | `surface-success-subtler` | `#EAF6EC` |

  --sf-primary-hover: var(--krds-light-color-button-primary-fill-hover);
  --sf-primary-pressed: var(--krds-light-color-button-primary-fill-pressed);
  --sf-primary-text: var(--krds-light-color-text-primary);
  --sf-primary-soft: var(--krds-light-color-surface-primary-subtler);
  --sf-text: var(--krds-light-color-text-basic);

### 4.2 상호작용 상태

| 상태 | 표현·동작 계약 |
| --- | --- |
| default | 기본 토큰과 레이블 |
| hover | 해당 모드의 상태 토큰. hover만으로 중요한 정보를 제공하지 않음 |
| active/pressed | 누르는 동안의 피드백. 업무 처리 완료나 선택 상태와 구분 |
| focus-visible | 배경과 구분되는 초점 표시. 고정 영역·overflow로 가리지 않음 |
| selected/checked | 지속 선택 상태. 색상 외 문구·표식·프로그램적 상태 제공 |
| indeterminate | 전체 선택 중 일부만 선택된 상태. checked와 구분 |
| disabled | 조작 불가 사유와 가능한 대안을 주변에서 확인 가능 |
| read-only | 값을 읽고 필요한 경우 복사 가능. 편집 불가 이유 제공 |
| loading | 처리 대상 표시, 중복 요청 방지, 실제 결과 전 성공 상태 금지 |
| error/success | 대상 필드·작업을 명시하고 해당 상태를 보조기술에 전달 |

정보는 파랑, 보완·확인 필요는 황색, 해당 작업의 완료는 초록, 오류·위험은 빨강을 기본으로 한다. ‘완료’ 색상을 보안 적합 판정으로 사용하지 않는다.

### 4.3 대비와 선명한 화면 모드

**가이드 기준:** 일반 텍스트 AA 4.5:1, 큰 텍스트 AA 3:1을 구분한다. 큰 텍스트 기준은 일반 24 CSS px 이상 또는 굵은 글자 약 18.67 CSS px 이상이다. 17px 본문을 큰 텍스트로 판정하지 않는다. (G25 p.122)

**프로젝트 수용 기준**

- 기본 본문은 **7:1 이상을 설계 목표**로 하고, 일반 텍스트 최소 4.5:1을 검증한다. G25 p.194의 기본 모드 본문 목표를 참고한다.
- 정보 전달에 필요한 입력 경계·아이콘·초점 표시는 주변과 3:1 이상을 검증한다. 장식적 패널 선에 일괄 적용하지 않는다.
- 모든 실제 전경·배경 조합, hover·오류·선택 상태를 검사한다. 팔레트 사용만으로 통과 처리하지 않는다.
- 선명한 모드를 제공할 때 본문 15:1, 헤딩·레이블 7:1을 목표로 한다. 의미를 전달하는 아이콘은 G25 pp.123·171의 7:1, 기타 시각 보조는 p.194의 4.5:1을 프로젝트 목표로 구분한다.
- 밝은 배경만 반전하지 않는다. 공식 `high-contrast` 토큰을 역할별로 연결하고 이미지·초점·레이어·상태도 검사한다.
- 모드를 바꾸거나 화면을 이동해도 선택을 유지한다. 모드 전환 때문에 정보나 기능이 사라지지 않아야 한다.
- 지원 여부는 배포 범위에 명시한다. 밝은 모드만 구현했으면 선명한 모드 지원 또는 표준형 전체 준수로 표시하지 않는다.

### 4.4 형태·간격·엘리베이션

G25는 컨테이너 크기와 역할에 따른 둥글기 계층, 엘리베이션과 오버레이를 정의한다. (pp.126–138·177–204)

- 기본 버튼·입력은 채택한 키트의 컴포넌트 토큰을 사용한다. 문서 예시값으로 공식 컴포넌트 CSS를 무조건 덮어쓰지 않는다.
- 새 커스텀 컨테이너는 프로젝트 선택값으로 **작은 요소 4px / 일반 컨트롤 6px / 카드 10px / 큰 패널·다이얼로그 12px**를 기본 집합으로 사용한다. 크기와 역할이 다르면 적용 근거를 기록한다.
- 콘텐츠를 자르는 `overflow: hidden`으로 모서리 모양만 맞추지 않는다. 초점 표시도 보존한다.
- 기본 패널은 테두리로 구분한다. 떠 있는 도움말·메뉴·모달의 계층에만 필요한 그림자와 오버레이를 사용한다.
- z-index는 공통 계층 토큰으로 관리한다. 중첩 모달을 기본 패턴으로 사용하지 않는다.
- 간격은 프로젝트 집합 `4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64px`를 사용한다. 가로 입력 조합 16px, 카드 간격 24px을 우선한다. (G25 p.157 참고)

## 5. 타이포그래피와 문장

**가이드 기준:** Pretendard GOV, 표준형 400/700, 줄 간격 150% 이상, rem 표현, Figma Vertical Trim Standard. (G25 pp.103–108)

### 5.1 프로젝트 글자 위계

| 용도 | PC | 작은 화면 | 굵기 | 적용 근거 |
| --- | --- | --- | --- | --- |
| 페이지 제목 | 32px / 3.2rem | 24px / 2.4rem | 700 | Heading large |
| 섹션 제목 | 24px / 2.4rem | 22px / 2.2rem | 700 | Heading medium |
| 패널·그룹 제목 | 19px / 1.9rem | 19px / 1.9rem | 700 | Heading small |
| 본문·중요 안내 | 17px / 1.7rem | 17px / 1.7rem | 400 | Body medium |
| 입력 레이블 | 17px / 1.7rem | 17px / 1.7rem | 400 | Label medium |
| 일반 도움말·보조 정보 | 15px / 1.5rem | 15px / 1.5rem | 400 | Body small |
| 비핵심 메타데이터 | 13px / 1.3rem | 13px / 1.3rem | 400 | Body xsmall, 제한적 사용 |

표는 G25 pp.111–117에서 선택한 **프로젝트 적용표**다. 정보 구조와 시맨틱 제목 레벨은 독립적으로 결정한다. 레이블의 필수·중요 부분에 700을 사용하는 것은 프로젝트 강조 규칙으로 관리한다.

- 중요한 입력 내용·오류·업무 상태·주요 버튼을 13px로 낮추지 않는다.
- 한 화면에 대표 `h1`을 하나 두고, 하위 제목을 정보 위계대로 제공한다.
- 문서 제목·신청 서비스명·부서명은 줄바꿈을 허용한다. **업로드 목록 파일명은 8.8의 한 줄 규칙**을 적용한다.
- 본문·입력의 기본 자간은 0으로 한다. 제목 자간은 적용한 역할 토큰을 사용한다.
- Pretendard GOV 실제 폰트 파일과 라이선스를 제공한다. 선언만으로 폰트가 설치되었다고 판단하지 않는다.
- 실제 400/700 파일 또는 해당 굵기를 지원하는 variable font를 사용한다. 합성 굵기에 의존하지 않는다.

```css
/* 100%가 16px인 기본 브라우저 설정에서 1rem ≈ 10px */
html { font-size: 62.5%; }
body {
  font-family: 'Pretendard GOV', 'Pretendard',
    'Noto Sans KR', 'Malgun Gothic', system-ui, sans-serif;
  font-size: 1.7rem;
  line-height: 1.5;
}
```

사용자가 기본 글자 크기를 바꾸면 위 환산값도 달라진다. 고정 px 높이로 텍스트 영역을 잘라내거나 브라우저 확대를 막지 않는다.

### 5.2 문구

| 피할 문구 | 사용할 문구 |
| --- | --- |
| 확인 | 답변 저장 / 협의 요청 / 설정 게시 / 최종 제출 |
| AI 보안 검증 완료 | AI 정보 추출이 완료되었습니다. 제안 내용을 확인해 주세요. |
| 저장되었습니다 | 설정 초안을 저장했습니다. 게시하면 새 신청부터 적용됩니다. |
| 잘못된 값입니다 | 목적지 IP를 입력하거나 ICT인프라 담당자에게 확인을 요청해 주세요. |
| 적용 성공 | 처리 결과를 기록했습니다. 실제 적용 여부는 첨부 근거에서 확인해 주세요. |

한국어 존댓말로 행동·대상·결과를 설명한다. 전문 용어에는 업무 맥락의 도움말을 제공한다. 운영 화면에 내부 스택 트레이스·서버 정보를 노출하지 않고 필요한 경우 문의용 요청 번호를 제공한다.

## 6. 화면 너비와 반응형

### 6.1 공식 참고값과 업무 확장값

G25 표준형의 최대 콘텐츠 너비는 **사이드 메뉴를 포함하여 1,200px**이다. (pp.147·150)

| 항목 | 보안길잡이 프로젝트 규칙 |
| --- | --- |
| 주요 설계 화면 | 1,920×1,080 PC. 작은 화면과 확대도 지원 |
| 업무 셸 최대 너비 | 1,920px, 중앙 정렬. 메뉴·본문 여백을 포함하는 외부 셸 |
| 왼쪽 메뉴 | 기본 240px |
| 본문 좌우 여백 | 일반 PC 40px / 넓은 PC 48px / 중간 화면 24px / 작은 화면 16px |
| 상세 화면 | 본문 + 검토 패널. 패널 최소 340px을 확보할 때만 2열 |
| 장문 폼 | 최대 약 880px 권장. 넓은 나머지 공간은 근거·도움말에 활용 |
| 입력 배치 | 단일 열 우선. 관련된 짧은 항목만 논리적 그룹 안에서 가로 배치 |
| 패널 내부 여백 | 기본 24px / 작은 화면 20px |
| 섹션 간격 | 일반 24px / 큰 업무 구획 32~48px |

1,920px는 최소 너비가 아니다. 전체 페이지에 강제 가로 스크롤을 만들지 않는다. `minmax(0, 1fr)`, `min-width: 0` 등으로 긴 콘텐츠가 그리드를 밀어내지 않게 한다.

### 6.2 분기점과 배치

G25 pp.145–146의 분기점과 그리드 범위를 참고한다. 아래 배치 동작은 프로젝트 규칙이다.

| 뷰포트 CSS 너비 | 칼럼 | 최소 화면 여백 | 배치 |
| --- | --- | --- | --- |
| 320~359px | 4 | 16px | 추가 검증 범위. 본문 1열, 메뉴 접기 |
| 360~767px | 4 | 16px | 폼 1열, 검토 패널을 본문 아래에 배치 |
| 768~1023px | 8 | 24px | 메뉴 접기·축소, 상세 기본 1열 |
| 1024~1279px | 12 | 24px | 실제 가용 폭에 따라 상세 1열 유지 가능 |
| 1280~1439px | 12 | 24px | 왼쪽 메뉴와 본문. 충분한 공간에서 2열 |
| 1440px 이상 | 12 | 24px | 와이드 구성, 최대 셸 너비 안에서 유동 확장 |

- 가터는 작은·중간 화면 16px, 큰 화면 24px을 우선한다.
- 320px 검증은 프로젝트 추가 기준이다. G25 표준형의 최적화 시작점 360px과 구분한다.
- 기관·진행 상태·오류·주요 행동을 작은 화면에서 제거하지 않는다.
- 고정 헤더·하단 버튼이 본문이나 키보드 초점을 가리지 않게 한다.
- 표는 의미 관계를 유지한 독립 스크롤 또는 카드형 재배치를 사용할 수 있다. 일반 폼·본문은 페이지 폭 안에 배치한다.
- 기본 글자 200% 확대와 브라우저 400% 확대에서 읽기·조작·재배치를 확인한다. 확대 시 실제 CSS 뷰포트 크기도 기록한다. (G25 pp.732–734 참고)
- 기존 1,100/1,350/1,700px 보조 분기는 화면별 예외다. 새 분기점과 무계획하게 중복 적용하지 않는다.

## 7. 공통 셸·내비게이션·역할

### 7.1 공통 셸

| 영역 | 포함할 내용 |
| --- | --- |
| 안내 영역 | 실제 운영 안내 또는 명확한 시연 표시. 적용 대상일 때 공식 배너 |
| 헤더 | 서비스 로고·이름, 주요 메뉴, 사용자·기관 문맥, 로그인 상태 |
| 왼쪽 메뉴 | 역할별 탐색, 현재 메뉴 강조 |
| 본문 시작 | 필요 시 브레드크럼, 바로 이어지는 페이지 제목·설명 |
| 업무 본문 | 진행 상태, 검색·입력·검토·문서 |
| 본문 끝 | 저장·다음 단계·완료 결과·도움말 |
| 푸터 | 운영 주체, 연락처, 개인정보 처리방침, 저작권, 필요한 안내 링크 |

**가이드 기준:** 아이덴티티·헤더·푸터·탐색 패턴은 G25 pp.220–338, G24 pp.114–235를 참고한다.

- 로고는 헤더 왼쪽 상단에 두고 홈으로 이동할 수 있게 한다. 이미지 로고에는 적절한 대체 텍스트를 제공한다.
- 헤더 구성 순서와 푸터 정보 순서를 화면마다 유지한다. 연락처와 링크의 실제 목적지를 점검한다.
- 시연과 운영의 푸터를 구분한다. 실제 운영 화면을 단순 시연 문구만으로 대체하지 않는다.
- 적용 대상인 공식 배너의 문구·스타일은 임의 변경하지 않는다. 운영기관 식별자는 실제 관리 주체를 확인해 제공한다.
- 유틸리티 링크가 5개 이상 필요하면 그룹·메뉴로 정리한다. 주요 작업 이름을 알기 어려운 아이콘만으로 숨기지 않는다.
- 이동은 링크, 실행은 버튼을 사용한다. 외부 서비스·새 창 이동은 구분해 알린다.
- 본문 인라인 링크는 밑줄 등 색상 외 단서로 구분한다. 전화·이메일을 제공하면 가능한 경우 적절한 링크를 연결한다.

### 7.2 탐색 계약

- 반복 영역을 건너뛰는 ‘본문 바로가기’를 문서 앞에 두고 실제 본문 초점 이동을 확인한다. 필요한 건너뛰기 링크는 3개 이내로 구성한다.
- 메인 메뉴는 최대 3수준, 사이드 메뉴는 최대 2수준으로 구성한다. 더 깊은 업무는 본문에서 점진적으로 탐색한다.
- 현재 메뉴에 시각적 표시와 `aria-current="page"`를 제공한다.
- 메뉴 확장을 마우스 hover에만 맡기지 않는다. 클릭·키보드로 열고 닫으며 확장 상태를 전달한다.
- 좁은 화면에서 사이드 메뉴를 접더라도 동등한 탐색 수단을 제공한다.
- 브레드크럼은 위치를 나타내며 업무 진행 단계를 대신하지 않는다. 홈/단일 계층 화면에는 불필요하게 표시하지 않는다.
- 브레드크럼은 홈부터 시작한다. 명확한 현재 페이지 제목이 바로 아래에 있으면 마지막 경로를 상위 화면으로 끝내는 방식을 사용한다. 중간에 다른 콘텐츠를 끼우지 않는다. (G25 p.284)
- 긴 경로는 계층을 정리하고 작은 화면에서는 처음·마지막 경로 중심으로 축약한다. 접근할 수 없는 경로를 가짜 링크로 만들지 않는다.
- 여러 기관을 관리한다면 현재 기관을 계속 표시한다. 기관 전환 전 저장하지 않은 편집 내용과 처리 중 작업의 영향을 알린다.

### 7.3 역할별 정보 구조

| 역할 | 기본 메뉴 | 중요한 정보 |
| --- | --- | --- |
| 신청자 | 신청 현황, 새 신청, 보완 요청, 문서함 | 현재 단계, 남은 입력, 담당자 요청 |
| 정보보안 | 협의 요청함, 담당 검토, 검토 이력 | 개인정보·외부 전송·권한·기록 정책 |
| ICT인프라 | 협의 요청함, 통신 정보, 처리 이력 | 출발지·목적지·프로토콜·포트·기간 |
| 기관 관리자 | 질문, 문서 양식, 검토 절차, 설정 버전 | 초안·게시본·적용 대상 |

역할과 기관 권한의 최종 판단은 서버가 한다. 시연용 역할 전환 드롭다운을 운영 권한 기능으로 사용하지 않는다. 설계 메뉴에 있다는 이유만으로 구현 완료로 간주하지 않는다.

## 8. 공통 컴포넌트 계약

### 8.1 버튼과 링크

근거: G25 pp.495–521, 특히 pp.513–520; G24 pp.368–381.

| 유형 | 용도 |
| --- | --- |
| Primary | **페이지 전체의** 가장 중요한 행동 1개 이하 |
| Secondary | 다음 순위 행동, 확인 요청 등 |
| Tertiary / Text | 임시 저장·목록 이동·추가 정보 등 보조 행동 |
| Danger | 삭제·폐기 등의 의미. 위험성에 맞는 확인 절차와 함께 사용 |

- 페이지의 각 패널·카드마다 Primary를 반복하지 않는다. 최종 제출이 Primary인 화면의 파일 선택은 하위 강조를 사용한다.
- 동일 그룹의 버튼 높이는 같게 한다. 긴 레이블 때문에 너비가 달라질 수 있으나 강조를 위해 높이를 달리하지 않는다.
- 가로 폼 행동 영역은 제출·다음 버튼을 오른쪽 끝, 다음 순위를 그 왼쪽, 취소·이전 등 3차 행동을 왼쪽으로 구분하는 방식을 기본으로 한다. 화면마다 정렬 규칙을 바꾸지 않는다.
- 세로로 배치하면 최상위 강조 행동을 첫 번째에 둔다. DOM·초점 순서가 시각적 순서와 어긋나지 않게 구현한다.
- 기본 크기는 키트 medium, 표 보조 행동은 small을 우선한다. 채택한 키트의 높이 48/40/56px 등은 계산된 스타일로 확인한다.
- 터치 대상은 **44×44 CSS px 이상을 프로젝트 수용 기준**으로 채택한다. 40px 보조 버튼을 터치 화면에 표시할 때는 크기나 실제 hit area를 확대한다. (G25 p.520의 권장값을 프로젝트 기준으로 채택)
- `<button>`의 `type`을 명시하고 Enter·Space 동작을 제공한다. 링크는 Enter로 이동한다.
- 처리 중 대상·대기 상태를 표시하고 중복 요청을 방지한다. 실패하면 재시도할 수 있게 복원한다.
- 비활성 사유는 주변 설명으로 제공한다. 마우스로만 확인 가능한 툴팁에 숨기지 않는다.
- 아이콘 버튼에는 기능을 설명하는 접근 가능한 이름을 제공한다. 장식 아이콘은 중복 낭독하지 않는다.

### 8.2 입력 폼·텍스트

근거: G25 pp.677–696·832–851; G24 pp.513–532·631–650.

- 폼 제목과 입력 그룹을 제공하고 단일 열을 우선한다. `<label>`과 입력을 연결하며 placeholder를 레이블·도움말 대용으로 사용하지 않는다.
- 필수·선택을 일관된 문구로 표시한다. 프로그램적 필수 속성과 실제 단계의 필수 조건을 일치시킨다.
- 도움말에는 형식·단위·작성 이유를, 오류에는 수정 방법을 제공한다. `aria-describedby`·`aria-invalid`를 실제 상태에 맞춰 연결한다.
- 검증 실패 시 사용자가 고칠 수 있도록 일반 업무 입력값을 보존한다. 여러 오류는 상단 요약과 필드 링크로 안내한다.
- 작성 중 불필요하게 초점을 빼앗지 않는다. 제출 실패 시 오류 요약 또는 첫 오류로 이동시키고 수정 후 오류 상태를 해제한다.
- 복사·붙여넣기를 제한하지 않는다. 한글 조합 중에 값을 잘라내거나 검색·제출을 실행하지 않는다.
- 글자 수 제한이 있으면 최대 길이와 현재 또는 남은 길이를 제공한다. 서버·클라이언트의 계산 기준을 맞춘다. 바이트 제한이면 사용자 설명과 문자 제한을 혼동하지 않는다.
- 반복되는 개인정보 입력에 적절한 `autocomplete`를 사용한다. 다른 사람·기관의 정보가 잘못 자동 입력되지 않게 확인한다.
- 필요한 데이터만 수집한다. 이전에 확인된 정보를 다시 입력시키기보다 검토·수정할 수 있게 제공한다.
- 입력값의 단위는 placeholder가 사라져도 확인할 수 있게 표시한다.
- 긴 폼은 임시 저장·마지막 저장 시각·복원을 제공한다. 저장 전후 상태를 정확히 구분한다.
- 필수 항목 미완료 시 버튼 비활성화는 가이드의 고려 사항이다. **프로젝트 기본은 제출 시 오류를 설명**하는 방식이며, 단계 선행 조건·권한 제한·전송 중에는 비활성화와 이유를 제공한다. 가이드 권장과 프로젝트 선택을 검증 기록에 구분한다.
- 취소·초기화·삭제를 제출 버튼과 명확히 구분한다. 입력 전체를 지우는 행동은 영향 안내와 확인을 제공한다.

### 8.3 라디오·체크박스·셀렉트·토글

근거: G25 pp.523–580; G24 pp.382–429.

| 선택 과업 | 컴포넌트·동작 |
| --- | --- |
| 소수의 상호 배타적 선택 | 라디오. 보안상 중요한 확인 질문은 임의 기본 선택 금지 |
| 여러 개 선택 또는 개별 동의·확인 | 체크박스. 상호 배타적 옵션 집합을 체크박스로 표현하지 않음 |
| 단일 선택 목록 | 셀렉트. 항목이 지나치게 많으면 검색 가능한 선택 UI 검토 |
| 즉시 적용되는 켜기/끄기 | 토글 스위치. 별도 저장이 필요한 선택과 구분 |

- 선택 묶음에 `fieldset`·`legend` 등으로 그룹 이름을 제공하고 레이블 클릭으로 선택할 수 있게 한다.
- 옵션은 논리적인 순서로 제공한다. 가나다순이 적합하지 않으면 업무 흐름·사용 빈도 등 이유를 기록한다.
- ‘선택해 주세요’는 값으로 저장하지 않는다. ‘모름’·‘미해당’·‘미입력’을 서로 다른 의미로 관리한다.
- 라디오에는 필요 시 ‘잘 모름/미해당’ 또는 선택 초기화 방법을 제공한다.
- 전체 선택은 선택 없음·일부 선택·전체 선택을 구분한다. 네이티브 checkbox의 `indeterminate` 등 실제 상태와 표현을 일치시킨다.
- 셀렉트 값 변경만으로 전체 폼을 제출하거나 사용자에게 예고하지 않은 화면 이동을 실행하지 않는다.
- 토글 레이블은 상태가 바뀌어도 유지한다. 서버 반영에 실패하면 상태를 복원하고 이유를 알린다.
- 기관 설정처럼 **초안 저장·게시가 필요한 편집**은 즉시 운영 반영으로 오해되는 토글을 피하고 체크박스·선택 필드를 사용한다.
- 라디오 방향키·체크박스 Space·셀렉트 기본 키보드 동작을 보존한다. 커스텀 구현은 같은 기능을 검증한다.

### 8.4 날짜·기간·기술정보

근거: G25 pp.664–676, 프로젝트 업무 규칙.

- 날짜의 의미와 형식(`YYYY-MM-DD` 등)을 입력 전에 설명한다. 시작일·종료일 레이블을 구분하고 순서 오류를 안내한다.
- 조회 기간 필터에는 시작·종료 범위를 제공한다. 운영 일시는 프로젝트 기본 표시 시간대 `Asia/Seoul`과 서버 계약을 맞춘다.
- 방화벽 적용 기간 등 정확성이 필요한 값은 추정 날짜를 확정값으로 저장하지 않는다. 모르면 ‘담당자 확인 필요’로 남긴다.
- IP·프로토콜·포트·시스템명은 필요한 형식과 예시를 제공한다. UI에서 유효해 보인다는 이유로 정책 적합으로 판정하지 않는다.
- 제출용 필수 기술정보를 초기 사업 설명 단계에서 모두 강제하지 않는다.

### 8.5 목록·표·검색·필터·페이지네이션

근거: G25 pp.317–338·459–470·798–802·857–877·913–972.

- 기본 순서는 제목 → 상태·담당 분야 필터 → 검색 → 결과 수·정렬 → 목록 → 페이지 이동이다.
- 검색 대상이 무엇인지 레이블로 설명하고 검색 실행·검색어 삭제 수단을 제공한다.
- 검색어·선택 조건·정렬·페이지 크기를 유지한다. 상세를 보고 돌아왔을 때 가능한 한 같은 목록 문맥으로 복귀한다.
- 적용된 필터를 문구·태그로 보여주고 전체 초기화를 제공한다. 기간 검색은 시작·종료 범위로 구성한다.
- 넓은 화면에서는 주요 필터를 숨기지 않는다. 작은 화면에서 축약해도 현재 적용 상태와 해제 수단은 확인할 수 있어야 한다.
- 결과 수, 조회 실패, 검색 결과 없음, 아직 접수된 자료 없음은 구분한다. 결과가 없으면 조건 변경·초기화 등의 대안을 제공한다.
- 실제 데이터에는 `table`, `caption`, `thead`, `th scope`를 사용한다. 정렬은 헤더의 버튼과 `aria-sort`로 전달한다.
- 양적 숫자는 오른쪽, 사업명·IP·신청번호 등 명목 정보는 왼쪽을 기본으로 한다. 단위와 날짜 형식을 통일한다.
- 빈 값의 의미가 단순 부재일 때는 대시를 쓸 수 있다. **미확정·미해당·미입력·권한 제한을 같은 대시로 숨기지 않는다.**
- 행 전체 클릭만 제공하지 않는다. 명확한 사업명 링크나 상세 링크로 진입할 수 있어야 한다.
- 좁은 모달·아코디언 안에 넓은 표를 억지로 넣지 않는다. 전체 상세 화면이나 적절한 재배치를 사용한다.
- 한 화면의 주 목록에 페이지네이션 하나를 두고 목록 하단 중앙에 배치한다. 현재·전체 페이지와 첫/끝·이전/다음 수단을 제공한다.
- 숫자 페이지 항목은 말줄임표 포함 PC 최대 10개, 작은 화면 최대 7개로 구성한다. 현재 페이지는 `aria-current="page"`로 전달한다.
- 페이지네이션과 무한 스크롤을 같은 목록에 혼용하지 않는다. 화면 폭이 바뀌었다고 전체 페이지 수가 바뀌지 않게 한다.
- CSV·문서 다운로드는 현재 필터 결과인지 전체 목록인지 명시한다. 조회·내려받기 권한은 서버에서 검사한다.

### 8.6 탭·단계 표시·접기

근거: G25 pp.379–386·405–415·445–458·582–588·1099–1100.

- 동일 영역의 조회 패널을 전환할 때 탭을 사용할 수 있다. ARIA 탭을 사용하면 역할·선택 상태·탭과 패널 연결·방향키 탐색을 함께 구현한다.
- 단순 상태 필터 버튼은 `aria-pressed` 등 해당 역할을 사용한다. 모양만 보고 `role="tab"`를 붙이지 않는다.
- **한 작성 단계의 신청 입력 섹션을 탭·아코디언·접힌 영역 뒤에 숨기지 않는다.** 조건에 따라 해당하지 않는 필드는 조건과 이유를 설명한다.
- 도움말·원문·과거 이력은 접을 수 있으나, 필수 입력·오류·중요 경고를 접힌 상태로만 제공하지 않는다.
- 작성 단계 표시와 전체 검토 진행을 구분한다. 단계 표시기의 3~7단계 권장을 참고하며, 보안길잡이 전체 업무는 4개 상위 단계로 표현한다.
- 현재 실제 단계는 `aria-current="step"`으로 전달한다. 사용자가 조회 중인 과거 단계와 구분한다.
- 과거 단계를 클릭해 보았다는 이유로 승인·협의 완료·제출 상태를 변경하지 않는다.
- 앞으로 이동할 수 있는 조건과 선택 단계의 건너뛰기 가능 여부를 명확히 표시한다.

### 8.7 모달·알림·도움말

근거: G25 pp.387–398·598–663.

- 모달은 간단한 확인·결정에 사용한다. 긴 기관 설정·복잡한 표·다중 파일 업로드는 별도 화면으로 제공한다.
- 일반 모달은 사용자 행동으로 연다. 세션 만료·긴급 안내 등 가이드가 설명하는 경우만 자동 표시를 검토한다.
- 제목과 설명을 연결하고 `dialog`/`aria-modal` 등 선택한 구현의 의미를 검증한다.
- 열면 모달 내부로 초점을 옮기고, 키보드·스크린리더의 탐색이 배경으로 빠지지 않게 한다. 닫으면 호출 위치 또는 타당한 다음 위치로 복귀시킨다.
- 닫기 아이콘은 시각적으로 오른쪽 위에 둘 수 있으나 **DOM에서는 본문·행동 뒤의 마지막 요소**에 둔다.
- 닫기가 가능한 모달은 Escape를 지원한다. 닫기·취소와 확정의 결과를 구분하며 명시적 취소 버튼을 제공한다.
- 내용이 길면 본문 스크롤과 행동 영역을 관리하되 확대 시 잘리지 않게 한다. 긴 편집을 모달로 해결하지 않는다.
- 토스트는 짧은 결과에 사용한다. 중요한 오류·미해결 보완 요청은 사라지는 토스트만으로 알리지 않는다.
- 툴팁은 추가 설명용이다. 초점·터치로도 접근 가능하게 하며 필수 안내를 툴팁에만 숨기지 않는다.
- AI 요약·인터뷰 도움말은 사용자 질문에 맞는 용어로 제공한다. 복잡한 설명은 도움 패널이나 상세 문서로 연결한다.

### 8.8 파일 전송·AI 분석·문서 다운로드

근거: G25 pp.697–714·852–856; G24 pp.533–549·651–655.

**가이드 기준:** 파일 선택만으로 서버에 업로드·저장하지 않고 폼 제출 행동을 기다린다. 업로드 목록의 긴 파일명은 한 줄로 표시하고 말줄임표를 사용한다. (G25 pp.708–709)

**보안길잡이의 프로젝트 적용 흐름**

1. **파일 선택:** 브라우저에서 이름·형식·크기·개수를 확인한다. 이 단계에서는 서버 전송·AI 분석을 실행하지 않는다.
2. **분석 요청 확인:** 전송 대상 파일, 사용 목적, 저장·처리 범위를 보여준다.
3. **‘파일 전송 및 AI 분석 시작’ 실행:** 분석 요청 폼을 사용자가 명시적으로 제출한다. 이때 파일을 전송한다.
4. **업로드·분석:** 단계별 진행·실패·재시도를 보여준다.
5. **결과 검토:** 원문 근거와 AI 추출 후보를 사람이 확인한다.
6. **최종 신청 제출:** 확인된 자료와 문서의 제출본을 별도 행동으로 확정한다.

위의 분석 요청 제출은 최종 신청 제출과 다른 과업이다. 버튼·안내·서버 상태 코드에서 둘을 구분한다. 이는 가이드의 자동 전송 금지 원칙을 업무에 적용한 프로젝트 설계다.

- 파일 선택 전에 실제 서버·파서가 지원하는 형식·크기·개수·처리 목적을 안내한다. 과거 시연 제한을 운영 정책으로 승계하지 않는다.
- 선택된 파일과 서버 저장 파일을 구분한다. 드롭했거나 선택했다는 이유로 ‘업로드 완료’로 표시하지 않는다.
- 명시적 전송 전 파일 제거·교체가 가능해야 한다. 전송 뒤의 삭제는 실제 저장 데이터에 미치는 영향을 알린다.
- 파일 선택 버튼은 추가 선택이 가능한 기본 상태를 유지한다. 정책상 제한이 있으면 이유를 설명한다.
- 업로드 목록의 파일명은 한 줄·말줄임표를 사용하되, **전체 이름 보기** 수단을 키보드·터치로 제공한다. `title` 속성만으로 해결하지 않는다.
- 잘못된 형식·크기 초과·개수 초과·빈 파일·전송 실패를 구분한다. 암호화 문서 등 분석 불가 조건은 실제 지원 범위에 맞춰 안내한다.
- 재시도는 실패한 작업을 대상으로 하며 중복 파일·중복 분석 작업이 생성되지 않게 서버와 연동한다.
- 처리 상태는 선택됨 → 전송 중 → 분석 대기/분석 중 → 결과 확인 필요/실패로 구분한다. 취소는 실제 취소가 지원될 때만 제공한다.
- 문서 카드에 문서명, 초안/제출본, 버전, 생성 시각, 확인 상태를 표시한다.
- 다운로드에는 ‘다운로드’ 동작과 형식·크기를 표시한다. 예: `보안성검토 초안 다운로드 [PDF, 240KB]`.
- 미리보기·다운로드·새 창 이동을 서로 구분한다. 최종 문서의 미확정 값을 빈칸으로 숨기지 않는다.

### 8.9 화면 설정·숨긴 콘텐츠·미디어

근거: G25 pp.727–752. 2025판에서 별도 장으로 제공된 내용을 프로젝트에 적용한다.

- 별도 글자·화면 크기 설정을 제공하면 ‘보통·크게’처럼 설명적인 레이블과 초기화를 제공하고 옵션은 5개 이내로 구성한다. 브라우저 기본 확대도 계속 사용할 수 있어야 한다.
- 화면 확대와 모드 선택을 실제 지원하는 경우에만 노출한다. 버튼만 있고 전체 화면에 적용되지 않는 설정을 제공하지 않는다.
- `.sr-only`는 보조 설명·접근 가능한 이름에 제한적으로 사용한다. 중요한 안내는 가능하면 모든 사용자에게 보이게 제공한다.
- 스크린리더가 읽어야 할 설명에 `display:none`, `visibility:hidden`, 0px 크기를 사용하지 않는다.
- 숨겨진 패널과 비활성 배경의 조작 요소에는 초점이 들어가지 않게 한다. 보조 설명을 시각적으로 숨기는 경우와 완전히 비활성화하는 경우를 구분한다.
- 로고·차트·이미지에 역할에 맞는 대체 정보를 제공한다. 장식 이미지는 중복 설명하지 않는다. 동영상 안내를 도입하면 자막·대체 수단을 함께 제공한다.

## 9. 역할별 화면과 신청 여정

### 9.1 신청자

**이용 안내 → 사업 등록 → 파일 분석 요청 또는 직접 입력 → 추출 후보 확인 → 기관별 질문 → 수집 결과 확인 → 사전 협의 → 보완 → 최종 제출 → 완료·결과 확인**

- 시작 전에 필요한 정보·서류·처리 흐름·제약·문의처를 안내한다. 지원하지 않는 연계·알림·발급을 제공한다고 표시하지 않는다.
- 질문마다 작성 이유와 책임 역할을 설명한다. 모르는 기술정보는 담당자 확인 요청으로 전달할 수 있게 한다.
- 인터뷰는 한 세션 내 완료를 전제하지 않는다. 임시 저장·복원·전체 답변 검토를 제공한다.
- 앞선 값 변경이 뒤의 질문·기술 검토·문서에 영향을 주면 영향을 알려주고 재검토 상태를 표시한다.
- 제출 전 핵심 답변·문서·미해결 항목·제출 대상·수정/철회 조건을 확인하게 한다. 확정과 돌아가기 수단을 모두 제공한다.
- 제출 성공 응답 뒤에 명시적인 완료 화면을 제공한다. 바로 목록으로 보내고 토스트만 띄우지 않는다.
- 완료 화면에는 프로젝트 규칙으로 신청번호, 제출 시각, 제출본 버전, 다음 단계, 결과 확인 링크를 제공한다.
- 접수·검토·처리 결과를 구분하고 이후 보완 내역과 제출 이력을 조회할 수 있게 한다.

근거: G25 pp.1052–1142, 특히 pp.1099–1104·1115–1126; G24 pp.856–945.

### 9.2 정보보안·ICT인프라 담당자

| 화면 | 기본 구성 |
| --- | --- |
| 요청함 | 상태 요약, 담당 분야, 검색·필터, 사업명·신청자·기한·상태 |
| 상세 본문 | 사업 정보, AI 요약, 원문 근거, 확인된 값과 미확정 항목 |
| 검토 패널 | 역할별 체크리스트, 의견, 보완 요청, 협의 완료 |
| 이력 | 요청·답변·변경·확인 내용, 담당자, 시각, 대상 버전 |

정보보안은 처리 정보·외부 전송·권한·기록 정책을, ICT인프라는 통신 구간·프로토콜·포트·기간을 중심으로 보여준다. 권한 범위 내에서 다른 역할의 문맥도 제공한다. 보완 요청에는 대상 항목·요청 이유·작성 책임을 연결한다.

### 9.3 기관 관리자

**기관·게시 버전 확인 → 질문·양식·절차 편집 → 유효성 검사 → 초안 저장 → 변경 검토 → 게시**

- 질문 문구, 저장 키, 형식, 필수 여부, 필수 시점, 작성 역할, 적용 조건을 구분한다.
- 저장 키는 데이터 계약이다. 문구 수정과 키 변경을 같은 변경으로 취급하지 않는다.
- 새 게시본은 새 신청에 적용하고 기존 신청은 생성 시점 설정 버전을 유지한다.
- 기존 신청에 새 설정을 적용할 때는 별도 이관·영향 안내·재검토 절차를 둔다.
- 초안 저장은 운영 반영이 아니다. 게시 확인에 대상 기관·변경 내용·영향을 표시한다.
- 게시 권한은 서버 정책으로 결정하며 일반 정보보안 역할에 자동 부여하지 않는다.
- 긴 양식·질문·절차 설정은 전용 화면으로 제공한다.

## 10. 업무 상태와 AI 결과 계약

### 10.1 전체 업무 단계

| 단계 | 의미 | 주요 행동 |
| --- | --- | --- |
| 사업 등록·인터뷰 | 목적과 필요 정보 수집 | 입력, 추출 후보 확인, 협의 요청 |
| 담당자 사전 협의 | 전문 정보 확인 | 보완 요청, 기술정보 확인, 초안 검토 |
| 사용자 보완·제출 | 요청 해결과 제출본 확정 | 답변, 문서 검토, 최종 제출 |
| 최종 검토·처리 | 제출본 검토와 처리 결과 기록 | 재검토, 결과 통보, 적용 기록 |

기관별 순차·병렬·조건부 검토를 지원하더라도 각 단계의 책임과 완료 조건을 숨기지 않는다.

### 10.2 상태 사전

| 대상 | 상태 예시 | 표시 원칙 |
| --- | --- | --- |
| 신청 | 작성 중, 사전 협의 중, 보완 중, 제출됨 | 전체 신청 상태 |
| 협의 | 검토 대기, 검토 중, 보완 요청, 협의 완료 | 담당 역할의 작업 상태 |
| 실제 처리 | 처리 대기, 처리 완료, 처리 불가 | 검토와 별도 상태 |
| 입력값 | 미입력, 미확정, 미해당, 확인 완료 | 값이 없는 이유까지 구분 |
| AI 값 | AI 제안, 사용자 확인, 담당자 확인 | 출처와 확인 주체 |
| 기관 설정 | 수정 초안, 게시됨, 이전 게시본 | 적용 여부와 버전 |
| 문서 | 작성 초안, 검토 초안, 제출본 | 편집 중 내용과 제출 당시 파일 |

‘모든 입력 완료’는 ‘보안 적합’을 뜻하지 않는다. ‘협의 완료’는 ‘방화벽 적용 완료’를 뜻하지 않는다. 보안성검토처럼 결과 통보로 종결되는 업무에 장비 적용 상태를 강제하지 않는다.

### 10.3 업무 제약

- 순차 검토는 선행 완료 후, 병렬 검토는 필요한 역할 모두 완료 후 진행한다.
- 조건 판단 정보가 없으면 미해당으로 생략하지 않는다.
- 중요 정보가 바뀌면 기존 확인을 재검토 대상으로 표시하고 변경 이력을 보존한다.
- 제출본은 당시 답변·문서·기관 설정 버전에 연결한다. 보완 제출은 새 개정본으로 남긴다.
- 동시 수정 충돌은 조용히 덮어쓰지 않고 비교·다시 불러오기·재적용 수단을 제공한다.
- 권한·완료 조건·버전·업무 전이의 최종 검증은 서버가 한다.

### 10.4 AI 제안

- 제안값, 출처 파일·위치, 원문 근거, 확인 상태, 확인 행동을 함께 제공한다.
- 근거가 없으면 ‘근거 확인 필요’로 표시한다. 존재하지 않는 IP·포트·시스템명·승인 사실을 확정값으로 채우지 않는다.
- 평가되지 않은 확신도 숫자를 보안 적합성이나 승인 가능성으로 표현하지 않는다.
- 사용자 확인을 받기 전에는 AI 값을 확인 완료로 바꾸지 않는다.
- AI 실패·시간 초과에도 직접 입력·담당자 문의·재시도를 제공한다.
- 분석 중 입력이 바뀌었으면 이전 입력 기준의 결과임을 알리고 최신 내용을 덮어쓰지 않는다.
- 모델의 답변을 서버 권한 판단이나 업무 전이의 근거로 사용하지 않는다.
- 사용자 입력·업로드 내용·AI 텍스트는 데이터로 취급한다. React 기본 이스케이프를 유지하고 검증 없는 HTML 삽입을 금지한다.

## 11. 로그인·세션·중단과 복구

근거: G25 pp.977–1051; G24 pp.782–855. 인증 방식별로 적용 대상을 구분한다.

### 11.1 로그인

- 로그인 진입점은 일관된 위치에 두고 작은 화면에서도 찾을 수 있게 한다.
- 실제 지원하는 기관 SSO·계정 로그인 방식만 제공한다. SSO 전용 서비스에 작동하지 않는 회원가입·비밀번호 찾기를 만들지 않는다.
- 계정 로그인을 제공하면 아이디 형식·도움말, 기본적으로 숨겨진 비밀번호와 표시 전환, 복사·붙여넣기를 지원한다.
- 일반 업무 입력값 보존과 인증 실패 처리를 구분한다. 비밀번호의 재입력·초점 정책은 해당 인증 흐름과 보안 요구에 맞춰 명시하고, 오류 때문에 입력 전체를 무조건 초기화하지 않는다.
- 로그인 완료 후 원래 수행하려던 허용된 업무로 돌아갈 수 있게 한다.

### 11.2 세션 만료

- 로그인 유지 시간에 제한이 있음을 사용자가 미리 알 수 있게 한다.
- 만료 안내는 **최소 20초 전**에 제공한다. 프로젝트 기본 설계값은 60초 전이며, 실제 서버 시간·네트워크 지연을 고려해 검증한다.
- 안내에는 남은 시간, **로그인 연장**, **로그아웃** 버튼을 제공한다.
- 시간 연장은 최소 10회 이상 가능하도록 구현 목표를 정한다. 서버·SSO 제약 때문에 충족하지 못하면 적용 불가 사유와 사용자 대안을 기록하고 자동 준수 처리하지 않는다.
- 연장은 서버 성공 응답 후 반영한다. 화면의 타이머만 늘리지 않는다.
- 만료 안내는 현재 작업을 유지하는 모달로 제공하며 키보드·초점 계약을 따른다. 카운트다운을 매초 과도하게 낭독하지 않는다.
- 만료 시 저장된 초안과 저장되지 않은 변경을 구분하고, 재로그인 후 허용된 범위에서 이어서 작성할 수 있게 한다.
- 세션 종료 후 민감한 화면이 계속 노출되지 않도록 한다. 복원을 위해 비밀번호·토큰을 업무 초안에 저장하지 않는다.

### 11.3 저장·복구

**프로젝트 규칙**

- 운영 초안은 권한이 적용된 서버 저장을 기본으로 한다. 민감한 개요서·망 정보의 브라우저 영구 저장을 기본값으로 사용하지 않는다.
- 저장 중·저장됨·저장 실패를 구분하고 마지막 성공 시각을 표시한다.
- 화면 이탈·기관 전환·로그아웃 시 미저장 변경이 있으면 영향을 안내한다.
- 분석 결과 복구·첨부 재사용은 원래 기관과 신청 권한을 다시 검사한다.
- 재시도·새로고침으로 중복 제출되지 않도록 요청 식별자·버전 등 서버 계약과 연동한다.

### 12.1 공통 접근성

- [ ] `lang="ko"`, 의미 있는 페이지 제목, 본문 바로가기, `main` 등 주요 영역이 있다.

- [ ] 입력·버튼·아이콘에 접근 가능한 이름이 있고 보이는 레이블과 일치한다.

- [ ] 모달 초점 진입·제한·복귀·Escape 적용 조건을 확인했다.
- [ ] 색상·모양·위치만으로 상태나 오류를 전달하지 않는다.
- [ ] 실제 상태별 대비와 터치 영역을 측정했다.

- [ ] 지원하는 화면 모드·설정에서 같은 정보와 기능을 사용할 수 있다.
- [ ] 동작 감소 설정을 존중하고 중요 정보가 애니메이션에만 의존하지 않는다.

## 13. React·Next.js·Spring Boot 적용

### 13.1 책임과 구조

| 계층 | 책임 |
| --- | --- |
| React | UI·입력 상태·초점·오류·로딩·컴포넌트 상호작용 |
| Next.js | 라우팅·페이지·레이아웃·렌더링, 필요 시 BFF |
| Spring Boot | 인증·기관 권한·업무 전이·AI 작업·문서 생성·버전·DB 트랜잭션 |

다음은 권장 구조다. 실제 저장소를 확인한 후 적용하며 기존 파일이 이 경로에 있다고 가정하지 않는다.

```text
app/                  페이지·레이아웃
components/ui/        버튼·입력·배지·모달·상태 안내
components/layout/    헤더·메뉴·푸터·본문 셸
features/requests/    신청·협의·보완·제출
features/admin/       질문·양식·절차·게시
features/auth/        로그인·세션 안내·복귀
styles/               공식 토큰 연결·프로젝트 확장
lib/api/              API 호출·응답 변환
public/vendor/krds/   고정 버전 CSS·폰트·아이콘을 직접 배포하는 경우
specs/                업무 상태·API·필드·검증 기록
design.md             공통 디자인 규칙
```

- 공식 CSS를 먼저 로드하고 프로젝트 스타일을 뒤에 적용한다. CSS reset·루트 폰트 크기를 중복 적용하지 않는다.
- 의존성 또는 로컬 정적 파일 중 관리 방식을 정하고 버전을 고정한다. 런타임 외부 CDN을 필수 조건으로 만들지 않는다.
- React가 관리하는 DOM에 KRDS DOM 조작 스크립트를 중복 실행하지 않는다. 선택한 React 컴포넌트 또는 검증된 래퍼에서 상태를 일관되게 관리한다.
- 경로 전환 시 페이지 제목·초점·현재 메뉴를 갱신하고 뒤로 가기의 목록 문맥을 보존한다.
- Next.js 정적 export에는 Spring Boot 서버가 포함되지 않는다. 실제 API·인증·파일 저장은 별도 배포와 연결이 필요하다.
- 서버 렌더링·Route Handler를 사용하는 경우 배포 런타임과 인증 경계를 명시한다.
- 클라이언트 역할·기관 ID·업무 상태만 믿고 서버 작업을 허용하지 않는다.
- 비동기 응답은 대상 신청·버전과 연결한다. 이전 요청의 응답이 새 입력을 덮어쓰지 않도록 한다.

### 13.3 입력 마크업 예시

아래는 KRDS 입력 스타일과 접근성 정보를 연결하는 부분 예시다. 해당 React 컴포넌트에서 `name`, `setName`, `error`를 정의하고, 저장·검증은 실제 이벤트와 API에 연결한다.

```tsx
<div className="sf-field">
  <label htmlFor="project-name">사업명 <span>필수</span></label>
  <input
    id="project-name"
    name="projectName"
    className="krds-input medium"
    required
    value={name}
    onChange={(event) => setName(event.target.value)}
    aria-invalid={Boolean(error)}
    aria-describedby={error ? 'name-hint name-error' : 'name-hint'}
  />
  <p id="name-hint">검토할 사업의 공식 명칭을 입력해 주세요.</p>
  {error && <p id="name-error">{error}</p>}
</div>
```

제출 시 오류 요약·초점 이동·라이브 안내를 별도로 연결한다. 모든 필드 오류를 동시에 assertive alert로 읽어 중복 안내하지 않는다. 위 예시만으로 완전한 입력 검증이 구현된 것으로 간주하지 않는다.

## 15. 자체 검증과 판정 기록

### 15.1 설계와 구현 검증 분리

| 구분 | 기록할 값 |
| --- | --- |
| 설계 반영 | 반영 / 부분 반영 / 미반영 / 적용 검토 필요 |
| 구현 검증 진행 | 미검증 / 검증 중 / 완료 |
| 구현 검증 판정 | P / F / E / N/A. 미검증이면 비워 둠 |

- **P:** 대상 조건과 검증 절차를 실제로 충족했다.
- **F:** 적용 대상이며 조건을 충족하지 못했다.
- **E:** 채택한 평가 기준에서 인정한 예외에 해당한다. 근거를 기록한다.
- **N/A:** 기준의 적용 대상·조건에 해당하지 않는다. 사유를 기록한다.

프로젝트에서 다르게 만들기로 했거나 아직 구현하지 않은 것은 자동으로 E/N/A가 아니다. 적용 대상 기능의 실패·미검증을 제외해 점수를 높이지 않는다.

C24의 판정 체계와 결과서 구성(pp.9–15)을 참고한다. C24는 2024.11의 1단계 자료이며 일부 상세 절차가 비어 있다. G25와 다른 내용은 원문·판본을 명시하고 프로젝트 검증 절차를 작성한다. C24 전체 항목을 G25 전체 범위나 접근성 인증으로 간주하지 않는다.
